# WCAG 3.2.1 On Focus — design notes

Why this criterion is built the way it is. The mechanics live in
[`generator/README.md`](../generator/README.md); this records the reasoning, and the two
bugs the fixtures caught. Companion to
[`2.1.2-no-keyboard-trap.md`](2.1.2-no-keyboard-trap.md), which it inverts in an
instructive way.

## Why it needed a probe

**3.2.1 On Focus (Level A):** when any user interface component receives focus, it must
not initiate a **change of context** — a change of user agent, viewport, focus, or
content that changes the meaning of the page.

The behaviour is not in the markup, so a skill reading `element_html` cannot judge it:

```js
element.addEventListener("focus", showHint);              // fine
element.addEventListener("focus", () => location.href = x); // fails
```

Two lines the same shape, opposite outcomes. What a component does when focused has to
be established by focusing it and watching what changed. Same reasoning as 2.1.2, where
`preventDefault()` on `Tab` and on `Ctrl+Tab` are two characters apart and opposite.

## The central insight, inverted from 2.1.2

These two criteria are near-mirror images, and holding both in mind is what keeps either
from being built wrong:

| | 2.1.2 No Keyboard Trap | 3.2.1 On Focus |
|---|---|---|
| the alarming signal | focus is contained in a loop | the DOM changed on focus |
| when that is **correct** | a modal dialog *must* contain focus | a hint, tooltip, or combobox expanding |
| what actually fails | containment with no way out | a change of **context** |
| what decides it | the recovery phases (Shift+Tab, Escape) | *which* thing changed |
| naive probe would | flag every good dialog | flag every good form |

So the recorded signals are split by how decidable they are, and that split is the design:

- **Unambiguous** — `focusMovedTo`, `navigatedTo`, `opened`, `submitted`. Each is a
  change of context by the definition in the SC. No judgement required, so the evidence
  asserts them.
- **Ambiguous** — `mutations`. A revealed hint and an opened dialog are *the same
  measurement*. Telling them apart means reading what appeared, so the markup goes into
  the column and the significance goes to the model.

## Three decisions worth recording

### Programmatic focus, not tabbing

`element.focus()`, not a Tab sweep. **Isolation** is the reason: 3.2.1 asks what *this*
component does when focused, and a Tab-driven sweep cannot separate "component N stole
focus" from "component N+1 was reached normally". `focus`/`focusin` fire identically
either way, which is what handlers listen for.

The cost is a real limit, recorded in `focusedVia` so the skill can abstain on it rather
than read silence as a pass: a handler gated on `event.isTrusted` or `:focus-visible`
never runs for programmatic focus, so the probe cannot see it.

### `window.open` and `form.submit` are overridden, not observed

Both overrides exist because the honest-looking approach fails silently:

- **`window.open`** — programmatic focus is not a user gesture, so a real popup would be
  **blocked by the popup blocker** and the probe would observe *nothing happening*.
  Recording the attempt survives that, and the attempt is what the criterion is about.
- **`HTMLFormElement.prototype.submit`** — calling `form.submit()` from script fires
  **no `submit` event at all**. That is specified HTML behaviour: it skips validation and
  the event. A capture-phase `submit` listener alone therefore misses the commonest
  auto-submit idiom in existence, and the fixture built to exercise it came back reporting
  only "navigated" — losing the fact that a form was submitted, and tearing the page down
  on the way past. Both mechanisms are kept: the listener still catches a submit driven by
  activating a real control.

### Element handles, not `domIndex` — the bug the pass fixtures caught

This is the one place where 3.2.1 must break with how every other probe in the repo
addresses elements, and the reason is structural.

Every other probe resolves elements by index into `document.querySelectorAll("*")`, which
is safe **because those probes do not change the DOM**. This probe exists to provoke DOM
changes. The moment a focus handler inserts a hint, every index after it shifts by one —
and the probe starts calling `.focus()` on the wrong elements.

It failed exactly where it would do the most damage. From the first capture:

```text
hint-revealed-on-focus.html     issued   focusHeld=False  movedTo=issued   <-- ?!
combobox-expands-on-focus.html  postcode focusHeld=False  movedTo=None
```

`#issued` was enumerated at `domIndex` 15 and lives at 16 once the hint `<p>` exists, so
the probe focused element 15 — and then reported that focus had *moved away* from a field
it had never focused. `movedTo=issued` is the tell: focus was exactly where it should have
been. On the combobox the shifted index landed on an `<li>`, which is not focusable, so
`.focus()` did nothing and `activeElement` fell back to `<body>`.

Both are **pass** fixtures, and both would have reported a spurious focus change — the
one signal that is asserted as a failure without judgement. The bug's shape is worth
remembering: it made the probe *stop testing what it claimed to test*, and it only
manifested on pages whose focus handlers were benign, because those are the pages that
mutate the DOM without moving focus.

A Playwright element handle survives mutation. `domIndex` is still recorded, for
reporting and for comparison against the other probes' output — it is just never used to
find the element again.

## Attribute-target identity is load-bearing

`mutations.attributeTargets` records the **target's** `tag`/`role`/`id`/`aria-modal`, not
just the attribute name. That is not extra detail for its own sake:

A dialog already in the DOM that merely becomes visible **adds no node at all**. The only
trace is `hidden` coming off a `role="dialog"` element. `modal-dialog-opens-on-focus`
exists to hold that path, and it captures as:

```text
added: 0   removed: 0   attributes: 2
  attribute "hidden" changed on <div role="dialog" aria-modal="true" #verify-dialog>
```

With counts alone, the worst defect in the suite is `added: 0` — indistinguishable from
nothing having happened.

A related fix on the evidence side: mutation detail is rendered for **every** component
that mutated, not only the ambiguous ones. The dialog case is *also* an unambiguous
failure (it moves focus), so an earlier version reported only "focus moved to Security
code" and dropped the dialog entirely — a correct verdict with the reason thrown away,
and indistinguishable from a field quietly handing focus to its neighbour.

## Determinism

`navigatedTo` stores a **path** (`/renew`), not an absolute URL. The static server binds
an ephemeral port, so the absolute form would differ on every capture, the dataset would
never diff clean against itself, and the regression check that protects every other suite
would be worthless. Two independent captures of the fail suite are byte-identical.

## Status

Mechanically complete. Each of the five defect fixtures fires exactly one unambiguous
signal, on the intended component, by a distinct mechanism; none of the five passes fires
any. Three passes are mutation-only, two are entirely unchanged. The shared capture path
was re-diffed against the 2.1.2 and 3.3.2 datasets with no drift.

**Unverified:** the model's own accuracy. `python -m src.run --input 3.2.1_dataset.csv`
needs `AZURE_OPENAI_ENDPOINT`, unset in this environment as it was for 2.1.2. Everything
through routing and evidence is checkable; recall and false-positive rate are not.

If a false positive does appear, it will be on `hint-revealed-on-focus` or
`combobox-expands-on-focus` — the two that mutate the DOM on focus and conform. The
lever, as for 2.1.2, is `BASE_SYSTEM_INSTRUCTIONS` in `src/classifier.py`, which still
describes only 4.1.3's inverted-silence rule and says nothing about criteria where an
alarming signal is expected behaviour.
