# WCAG 3.2.2 On Input — design notes

Why this criterion is built the way it is, and the leak the isolation check caught.
Mechanics live in [`crawler/README.md`](../crawler/README.md). Companion to
[`3.2.1-on-focus.md`](3.2.1-on-focus.md), whose probe this one is the sibling of, and
to [`2.1.2-no-keyboard-trap.md`](2.1.2-no-keyboard-trap.md), whose advisory clause it
repeats.

## Why it is a separate probe, not a flag

**3.2.2 On Input (Level A):** changing the setting of any user interface component must
not automatically cause a change of context **unless the user has been advised of the
behaviour before using the component**.

It shares almost everything with 3.2.1 — the recorders, the element enumeration, the
record shape, the evidence helpers. Two things it does not share, and each is load-bearing.

**The trigger differs.** 3.2.1 fires on receiving focus; 3.2.2 on changing a setting.
That is not a detail: the repo holds *the same page* in both suites, as a 3.2.1 **pass**
(`navigation-on-activation-not-focus.html`) and a 3.2.2 **fail**
(`select-navigates-on-change.html`). Focusing the select does nothing; changing it
navigates. One page, two criteria, opposite verdicts, and the event name is the only
difference between them.

**3.2.2 has an exception and 3.2.1 has none.** A warning before the control makes
identical behaviour conform. So unlike every other criterion in this repo, the *same
measurement* can be a pass or a fail, and the deciding evidence is text rather than
behaviour.

## Focus first, arm second

A setting cannot be changed without focus touching the control first. With the recorders
armed any earlier, **every 3.2.1 on-focus defect would be recorded a second time here as
an on-input defect** — the same fixtures, flagged twice, with nothing in the data to say
which criterion was actually at fault.

So the order per component is: focus → settle → **arm** → change the setting → read.
Whatever the focus handler did happens outside the measurement.

### The leak the crossover check caught

The plan called for capturing the **3.2.1 fail fixtures under `--sc 3.2.2`** and
requiring no on-input change of context. First run:

```text
focus-jumps-to-another-field.html    on-input: card-number=focus-moved
modal-dialog-opens-on-focus.html     on-input: address-line=focus-moved
CROSSOVER LEAKS: 2
```

The ordering was right; the *comparison* was not. `focusHeld` was measured as
"is this component's handle the active element" — but on those two pages the focus phase
had already moved focus away, before any recording began. The component was legitimately
unfocused for reasons that had nothing to do with its setting changing, and the probe
called that an on-input focus change.

The fix is to take a baseline: capture whatever holds focus *after* the focus phase and
compare the after-state to **that**, so "focus moved" can only mean "moved because the
setting changed". Leaks went to zero, and the three fixtures that were already clean
(submit, window-open, navigate) stayed clean — those had never leaked, because their
effects were recorded through the arm/disarm boundary rather than by comparison.

Worth noting what this says about the check itself: three of five mechanisms were
isolated correctly by the ordering alone, and the failure was confined to the one signal
derived by comparison rather than by observation. A crossover check on fewer fixtures, or
on the wrong three, would have passed.

## Why buttons and links are not probed

`SETTABLE` omits `button` and `a[href]` deliberately. Activating one is a **request** —
the user asked for whatever happens next — which 3.2.2 permits outright and 3.2.5
governs. Including them would flag every "Go" button on the web, including
`select-requires-go-button.html`, which exists in the pass set precisely because moving
navigation onto a button is the recommended fix for a jump menu.

## The advisory, and why `hasText` is not `wasAdvised`

The exception is the pass condition, so the advisory is captured rather than inferred —
the same reasoning as 2.1.2, where "advised of the method" decides whether a contained
dialog conforms.

Three fields, of different strength:

| field | strength |
|---|---|
| `describedBy` | strongest — `aria-describedby`, announced as part of the control |
| `precedingText` | real but weaker — non-interactive text before it in its group |
| `label` | **not advice** — a name identifies a control, it does not warn about it |

**Labels destroyed the signal in the first implementation.** They were folded into
`describedBy`, on the reasoning that a label is text attached to the control. Every
control on every page has one, so the flag came back true for all ten fixtures including
the bare no-JS form — and the one comparison this criterion turns on stopped separating:

```text
before:  select-navigates-on-change              adv=YES
         select-navigates-on-change-with-warning adv=YES

after:   select-navigates-on-change              adv=none
         select-navigates-on-change-with-warning adv=YES
```

The flag is `hasText`, not `wasAdvised`, for a related reason. It means "there is text
here worth reading", not "the user was warned". A hint reading "We only use this to send
you updates" sets it true and advises nobody of anything. Whether wording actually warns
of a change of context is a judgement about language, and it stays with the model — the
same split as 3.2.1's ambiguous mutations.

Ordering is part of the SC ("*before* using the component"), so the `precedingText` walk
stops at the control: a warning printed underneath is not a warning. Text inside other
controls is skipped, or a `<select>`'s own option list reads back as advice — the trap
the 2.1.2 region capture hit and the reason the exclusion rule was reused here.

## An incident worth recording: a NUL byte in the source

Mid-build, `grep` began reporting `crawler/lib/vsr.js` as a binary file. A single NUL
byte had been written into the advisory block, inside
`CSS.escape(el.id || "\0")` where a space was intended. The file still parsed and the
probe still ran, so nothing failed loudly — it only surfaced because a search stopped
working.

Two things followed. The awkward `el.id || " "` guard was dropped in favour of testing
`el.id` before querying at all, which is clearer anyway; and `node --check` on both
touched modules became part of the verification, since a syntax-level corruption that
still parses is exactly the kind of thing a behavioural test will not catch.

## Determinism

`navigatedTo` stores a path, not an absolute URL — the static server binds an ephemeral
port, so the absolute form would differ every capture and the dataset would never diff
clean against itself. Two independent captures of the fail suite are byte-identical.

## Status

Mechanically complete. Every defect fixture fires exactly one unambiguous signal by a
distinct mechanism (submitted / window opened / navigated / focus moved / content
replaced); no passing fixture fires any; the crossover check reports zero leaks; captures
are byte-identical across runs. The shared-code changes (the `armContextRecorders`
rename, the `visibleHandles` generalisation) were re-diffed against the 3.2.1 and 3.3.2
datasets.

**Unverified:** the model's own accuracy. `python -m src.run --input 3.2.2_dataset.csv`
needs `AZURE_OPENAI_ENDPOINT`, unset here as it was for 2.1.2 and 3.2.1. Everything
through routing and evidence is checkable; recall and false-positive rate are not.

The false positive to expect is `select-navigates-on-change-with-warning` — it navigates
on input exactly like the failing fixture and conforms only by the exception, so it is
the page most likely to be condemned by a model reading the behaviour and stopping there.
